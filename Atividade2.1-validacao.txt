### Verificação de Artefatos Machine-Readable

Este exercício não exige AGENTS.md ou skill — mas o `README.md` do `.mcp/` funciona como documento normativo e é avaliável sob a mesma lente.

**O que está prescritivo e operacional:**
- A tabela de índice com permissão por server é diretamente consumível por qualquer membro do time.
- A seção "Política de alterações" lista 4 regras numeradas com critérios concretos (ex: "revisão de escopo pelo Tech Lead: confirmar que nenhuma pasta sensível foi adicionada").
- A restrição crítica do server `mcp-learning-everything` está em negrito com instrução explícita de remoção após onboarding.
- As justificativas de least privilege seguem o padrão "Por que esse server / Por que o escopo é mínimo / Risco de escopo mais amplo" — útil para revisão de PR.

**O que poderia ser mais prescritivo:**
- A seção de controle de escrita do `memory` diz "apenas papéis com autoridade [...] adicionam entidades" mas não define uma lista nominal de quem pode escrever em cada sessão — um agente não saberia operacionalmente quem autoriza.
- O README não define o formato esperado de entidades no grafo de memória (ex: template de nó para linguagem ubíqua), o que tornaria o `memory` server mais governado.

### Pontos Fortes

1. **Separação de instâncias como estratégia de sinalização** — a decisão de usar `filesystem-docs-readonly` e `filesystem-corpus-readonly` como instâncias nomeadas separadas, em vez de uma única instância com política documentada, é uma escolha de design bem fundamentada. O participante documenta a limitação (não é read-only técnico) e justifica por que a abordagem ainda é adequada para o contexto.

2. **Evidência de execução real e abrangente** — a transcrição mostra os três casos exigidos pelo enunciado: leitura de documento (`docs/novatech/`), recuperação de chunk com citação exata do corpus (`Chunk POL-001-A`) e consulta ao histórico git (commit hash, autor, data, mensagem). A demonstração vai além do mínimo — o agente também responde corretamente sobre exceções ao prazo de devolução, mostrando que o retrieval funciona de ponta a ponta.

3. **Análise de riscos com profundidade e honestidade** — 4 riscos identificados (2 além do mínimo), cada um com impacto, probabilidade, mitigação implementada e mitigação adicional recomendada. O participante distingue o que já foi feito do que ainda precisa ser feito, e separa claramente os riscos do ambiente local dos riscos que persistiriam em produção.

---

### Pontos de Melhoria

1. **Ausência de evidência de uso do GitHub Copilot** — o enunciado especifica Copilot como ferramenta para a Tarefa 2 (escrever o `.mcp/mcp.json`). Não há nenhum print, export ou menção de uso do Copilot. Em exercícios futuros que especificam uma ferramenta, incluir evidência explícita — mesmo que o resultado seja equivalente — é necessário para a avaliação da dimensão de ferramentas. Se a substituição foi intencional (ex: Copilot não disponível), documentar o motivo.

2. **Política de escrita no grafo `memory` sem operacionalização** — o README define quem pode escrever no grafo por papel (Tech Lead, PS, Delivery Manager), mas não há formato de entidade, template de nó, ou processo de revisão de entidades existentes. Adicionar um exemplo de entidade bem formada (ex: `{ name: "frete-especial", type: "termo-ubíquo", definition: "carga acima de 500kg", source: "PROC-042-v2" }`) tornaria o server `memory` governado de forma concreta, não apenas declarada.

3. **O server `git` aponta para raiz (`.`) — justificativa poderia ser mais robusta** — o participante justifica que o git server precisa de escopo global porque "o histórico é global ao repositório". Isso é correto, mas vale mencionar explicitamente que isso expõe metadados de arquivos que não estão no escopo do filesystem (ex: `git show` pode exibir conteúdo de `.env` se esse arquivo já foi commitado). A mitigação (`.gitignore` + `.env.example`) está correta mas está no Risco 1, não na justificativa do git server — um leitor poderia não conectar os dois.
