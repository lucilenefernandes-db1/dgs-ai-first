### Pontos Fortes

1. **Ciclo de avaliação estruturado com prompt de checklist**: o participante não apenas pediu ao Claude "avalie as respostas" — construiu um prompt de avaliação com critérios binários (sim/não) para cada ponto verificável, incluindo a instrução explícita de identificar em qual regra do system prompt uma eventual falha se originaria. Isso transforma a avaliação em uma auditoria reproduzível, não uma opinião subjetiva.

2. **Identificação de fragilidades latentes vs. falhas confirmadas**: a distinção entre "falha que ocorreu" e "superfície de risco que poderia ocorrer" revela maturidade técnica que vai além do exercício. A Fragilidade 2 (vedação de estimativas disfarçadas) é especialmente sutil — o model poderia ter respondido "o frete fica entre R$ X e R$ Y com os multiplicadores disponíveis" sem violar a letra da Regra 2, mas violando o espírito. O participante fechou essa brecha preventivamente.

3. **Tabela comparativa v1 → v2 com diff preciso**: a entrega inclui uma tabela que documenta exatamente o que mudou entre versões, com o texto antigo e o texto novo lado a lado. Isso torna a iteração auditável — qualquer revisor pode verificar que as mudanças são precisas, cirúrgicas e motivadas pelas fragilidades identificadas, sem alterações desnecessárias no que estava correto.

### Pontos de Melhoria

1. **Testes com v2 não cobrem casos novos**: as respostas v2 foram geradas para as mesmas 3 perguntas da v1. O ideal após uma iteração de system prompt seria testar pelo menos uma pergunta que exercite especificamente as mudanças introduzidas — por exemplo, uma pergunta com exceção enterrada em chunk secundário (para testar a nova instrução de varrer todos os chunks) ou uma pergunta onde fatores parciais estejam disponíveis e o risco de estimativa disfarçada seja real. Sugestão: acrescentar 1-2 perguntas adicionais na rodada de testes v2 que targeteiem as fragilidades corrigidas.

2. **Estimativa de tokens do sistema prompt poderia ser validada instrumentalmente**: a tabela de estrutura de contexto apresenta estimativas baseadas na regra 0,75 palavras/token, o que é metodologicamente correto. No entanto, o participante poderia ter incluído uma linha de validação — por exemplo, contar as palavras de cada seção explicitamente ou usar a API de tokenização para confirmar os valores. Em produção, a diferença entre "~230 tokens" estimado e o valor real pode ser relevante para o orçamento. Sugestão: incluir contagem de palavras explícita por seção na próxima versão da tabela.

3. **Ausência de teste para o caso de conflito entre chunks**: o system prompt tem uma instrução bem formulada para chunks conflitantes (Seção 3, "Conflito entre chunks"), mas nenhuma das 3 perguntas testadas exercita esse caminho. Uma pergunta com dois chunks apresentando valores contraditórios para o mesmo item testaria se essa instrução funciona na prática. Sugestão: incluir esse caso no conjunto de testes da v2 ou documentar explicitamente que o teste de conflito ficou para a próxima rodada.
